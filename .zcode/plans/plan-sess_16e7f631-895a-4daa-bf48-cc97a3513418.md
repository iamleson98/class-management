# Implementation Plan

## Overview
Three major tasks: (1) Swagger JSON endpoint in Go backend (dev-only), (2) Frontend API generation script, (3) Refactor all LMS listing APIs to follow the students pattern.

---

## Task 1: Swagger/OpenAPI JSON Endpoint (Dev Only)

### 1.1 Generate OpenAPI JSON at build time
- Add a Makefile target `build-json` that runs after `build-v4`, converting the YAML spec to JSON using `node -e` (yaml→json via built-in YAML parsing or a lightweight script)
- Output: `api/v4/html/static/mattermost-openapi-v4.json`

### 1.2 Embed the JSON in the Go binary
- Create `server/channels/api4/swagger_embed.go` with `//go:embed` directive pointing to the JSON file (using a relative path or build-time copy)
- Use build tags: the file only exists when built from the project root with the api target

### 1.3 Serve the endpoint (dev-only)
- Create `server/channels/api4/swagger.go` with build tag `!production`
- Register route `GET /api/v4/lms/openapi.json` in the LMS router (or `GET /api/v4/openapi.json` on the API root)
- Handler reads the embedded JSON and serves it with `Content-Type: application/json`
- A companion file `swagger_production.go` with build tag `production` that does NOT register the route (empty or no-op)
- Uses `model.GetServiceEnvironment() != "production"` as a runtime safety check in addition to build tags

### Files to create/modify:
- `server/channels/api4/swagger_dev.go` (new, `//go:build !production`)
- `server/channels/api4/swagger_production.go` (new, `//go:build production`)
- `server/channels/api4/lms_api/api.go` (add swagger route registration)
- `api/Makefile` (add `build-json` target)

## Task 2: Frontend API Generation Script

### 2.1 Install codegen dependencies
- Add `openapi-typescript` and `openapi-fetch` as devDependencies in `lms-fe/package.json`
- These are lightweight (~5KB gzip) and complement the existing fetch pattern

### 2.2 Create generation script
- Create `lms-fe/scripts/generate-api.ts` (or `.mjs`)
- The script:
  1. Fetches `http://localhost:8065/api/v4/lms/openapi.json` from the running backend (or accepts a file path as fallback)
  2. Runs `openapi-typescript` to generate TypeScript types into `lms-fe/src/lib/schemas/openapi-types.ts`
  3. Optionally generates the fetch client into `lms-fe/src/lib/api-client.ts`

### 2.3 Add npm script
- Add `"generate:api": "bun run scripts/generate-api.ts"` to package.json scripts
- The generated types file will be a companion to the existing hand-written types

### Files to create/modify:
- `lms-fe/scripts/generate-api.ts` (new)
- `lms-fe/package.json` (add devDependencies + script)
- `lms-fe/src/lib/schemas/openapi-types.ts` (generated output, added to .gitignore)

## Task 3: Refactor All Listing APIs to Follow Students Pattern

### Target Pattern (from students):
1. **FilterOpts embeds `utils.SearchOpts[T]`** — provides `limit`, `offset`, `count_total`, `where_ands`, `where_ors`, `orderings`
2. **POST method with JSON body** — decode body into FilterOpts struct
3. **Store returns `(Slice, int64, error)`** — items + true total count
4. **Two-query pattern** — fetch paginated results, optionally run count query when `CountTotal=true`
5. **Generic query builder** — uses `WhereCond`, `WhereAnds`, `WhereOrs`, `OrderBy` from `utils` package
6. **Handler response**: `utils.ResponseList{Items, TotalCount}`

### Entities to refactor (11 total):

#### A. FilterOpts refactor (`server/public/model_helper/lms.go`)
Each FilterOpts struct changes from:
```go
type ClassFilterOpts struct {
    CourseID   string
    Status     string
    TeacherID  string
    Page       int
    PerPage    int
    CountTotal bool
}
```
To:
```go
type ClassFilterOpts struct {
    utils.SearchOpts[utils.ClassColumn]
    CourseID   string `json:"course_id"`
    Status     string `json:"status"`
    TeacherID  string `json:"teacher_id"`
    Search     string `json:"search"`
}
```
- `Page`/`PerPage` → replaced by `Limit`/`Offset` in embedded `SearchOpts`
- `CountTotal` → moved into `SearchOpts`
- Add `Search string` field where applicable (for text search across name/email/phone fields)
- Each entity-specific FilterOpts embeds `utils.SearchOpts[EntityColumn]`

#### B. Store interface changes (`server/channels/store/lms_store.go`)
Replace separate `GetAll(opts) (Slice, error)` + `Count(opts) (int64, error)` with single `Search(opts) (Slice, int64, error)` for each entity.

#### C. Store implementation changes (`server/channels/store/sqlstore/lms_store/*.go`)
Refactor each `GetAll` + `Count` into a single `Search` method following the `SearchStudentUsers` pattern:
1. Build base `[]qm.QueryMod` with entity-specific filters
2. Use `WhereOrs` for search fields (ILIKE patterns)
3. Append `&opts.SearchOpts` for pagination/ordering
4. Run paginated query
5. If `opts.CountTotal`, clone mods with `opts.SearchOpts.ExludePaginationForCount()` and run count query
6. Return `(results, totalCount, nil)`

#### D. App layer changes (`server/channels/app/lms/*.go`)
Update each `Get{Entity}s(opts)` to return `(Slice, int64, *model.AppError)` and call the new `Search` store method.

#### E. API handler changes (`server/channels/api4/lms_api/*.go`)
For each entity:
1. Change route from `GET /entities` to `POST /entities`
2. Move create to `POST /entities/create`
3. Decode JSON body into FilterOpts (not query params)
4. Get `(items, totalCount, err)` from app layer
5. Return `utils.ResponseList{Items, TotalCount}`
