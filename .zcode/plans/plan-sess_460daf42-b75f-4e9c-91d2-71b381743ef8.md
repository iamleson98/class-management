## Chat Integration Plan — class-scoped chat in lms-fe

### Decision recap (from your answers)
- **Native rebuild** of the chat UI inside lms-fe's own stack (shadcn/ui + React Query + Zustand), reusing `src/chat/` only as a UX reference. The vendored Redux webapp stays un-wired.
- **Backend hooks + DB column** for provisioning — every enrollment path stays in sync, not just the UI one.

### A note on the "teams" question (you asked me to decide)
The backend's Mattermost core organizes channels under **Teams** (top-level containers). I'll use a **two-team** split, which cleanly satisfies your teaching-vs-operations intent and the "better focus" requirement:
- **`teaching` team** → holds one **private channel per class** (teacher + enrolled students + admins). This is where class chat lives.
- **`operations` team** → holds channels for management/ops (staff-only). Created once at provisioning time, not per-class.

A user logging in sees only the channels they're a member of (Mattermost enforces this natively via `GET /users/{user_id}/teams/{team_id}/channels`), so students only see their class channels — exactly your "better focus" requirement. Admins get added to every class channel as `channel_user` (moderator/support) automatically.

### Real-time strategy
The WebSocket endpoint can't reliably carry the `MMAUTHTOKEN` cookie cross-origin (Next.js rewrite is HTTP-only; prod uses `app.${DOMAIN}` vs `api.${DOMAIN}` with `SameSite=Lax`). So I'll implement real-time via **REST polling** (React Query `refetchInterval`) — reliable today with zero cookie gymnastics. The architecture is built so a WebSocket client can be slotted in later once frontend+backend share an origin.

### 2. Regenerate the SQLBoiler `Class` model

If regeneration tooling is broken/blocked, I'll hand-edit the generated file in the same style as the existing fields (clearly the only practical fallback) and note it.

### 3. New chat-provisioning helper
`server/channels/app/lms/chat.go` — new file in the `lms` package. Since `LMSApp` only holds a `store` (not the main `*App`), and all channel/team methods live on the main `*App`, the provisioning functions take the caller's `*App` as a parameter. Functions:
- `EnsureTeachingTeams(app)` → lazily creates `teaching` + `operations` teams (idempotent via `GetTeamByName`); caches their IDs in a config constant/naming convention so provisioning is deterministic.
- `ProvisionClassChannel(app, rctx, class, teacherID) (*model.Channel, AppError)` → if `class.ChatChannelID` is empty: create a **private** (`P`) channel named `class-{code}` in the `teaching` team, add the teacher + all admins as members, persist `ChatChannelID` back to the class row.
- `SyncChannelMembership(app, rctx, channelID, userIDs)` → add missing members, remove members no longer enrolled (idempotent diff).
- `CloseClassChannel(app, rctx, channelID)` → **permanently deletes** the channel and all its posts (`App.PermanentDeleteChannel` wipes posts — satisfies "all messages deleted").

Admin discovery for "admin in all channels": query users with `lms_super_admin`/`lms_admin` roles via `App.GetUsersByUsernames` or a role filter.

### 4. Wire hooks into existing handlers
Edits to `server/channels/api4/lms_api/class.go` (the handler layer has `c.App` = main App):
- **`createClass`** → after `c.App.LMS().CreateClass(...)`, call `lms.ProvisionClassChannel(c.App, rctx, class, class.TeacherID)`. Class creation + channel creation become atomic-ish; on channel failure, log + proceed (class still created, channel reprovisionable later) so a chat outage never blocks class management.
- **`enrollStudents`** → after `c.App.LMS().EnrollStudents(...)`, call `lms.SyncChannelMembership(...)` to add the newly enrolled students' userIds to the class channel. (`student_classes.student_id` already holds the Mattermost `users.id`, so it's a direct member add.)
- **"Class finish"** → there is no dedicated close endpoint today. I'll add the channel-cleanup to the existing `deleteClass` handler (call `lms.CloseClassChannel` before deleting the row), **and** hook into `updateClass` when `status` transitions to `CLOSED`/`CANCELLED`. This covers both "delete the class" and "mark it finished".

### 5. (No new permissions needed)
Reuses `PermissionLmsManageClasses` gating already on these handlers. Channel creation runs as the system (the server's own context), so a teacher creating a class gets the channel without needing channel-admin perms themselves.

## Frontend changes (lms-fe)

### 6. Chat API client
`src/lib/chat-api.ts` — a focused client for the Mattermost REST surface, using the **existing `authHeaders()` + `credentials:'include'` + `/api/v4` base** (same auth as the rest of lms-fe, zero new auth code):
- `getMyTeams()`, `getChannelsForUser(teamId)` → channel list scoped to the user.
- `getChannelPosts(channelId, page)` → messages (paginated).
- `createPost(channelId, message, fileIds?)`, `editPost`, `deletePost`.
- `getChannelMembers(channelId)`, `uploadFile(channelId, file)`.
- Channels are linked to classes by name convention `class-{code}` (matches the backend), so the class list can cross-reference to show class names/teacher info on each channel.

Self-contained types in `src/lib/chat-api.ts` (the OpenAPI spec has the chat paths inline but no exported interfaces, so I'll define `ChatChannel`, `ChatPost`, `ChatUser` interfaces modeled on `model.Channel`/`model.Post`).

### 7. Chat UI module
`src/components/lms/chat/` — new folder, matching the existing role-folder pattern:
- `chat-view.tsx` — main layout: left channel list, right message thread + composer (matches lms-fe's shadcn/ui styling, sky/teal theme, dark-mode aware).
- `channel-list.tsx` — shows only the user's channels (teachers see their class channels; students see theirs; admins see all). Badged with class code + member count. Real-time via React Query `refetchInterval`.
- `message-thread.tsx` — renders posts (markdown via the already-installed `react-markdown`/`rehype-raw`), date separators, own-vs-others styling, file attachments. Reverse-infinite-scroll for history.
- `message-composer.tsx` — textarea with send-on-Enter, file upload via existing `/api/v4/uploads`, optional typing indicator stub.
- Reuses `src/components/lms/shared/avatar.tsx` for sender avatars.

### 8. Navigation wiring
`src/app/page.tsx` + `src/store/lms-store.ts`:
- Add `'chat'` to the `ActiveView` union and to **every role's NAV array** (admin, teacher, student, counselor, parent — chat is relevant to all, scoped server-side by membership). Use the `MessagesSquare`/`MessageCircle` lucide icon, section "Communication".
- Add `case 'chat': return <ChatView />` to `renderView` for all roles (one shared component, behavior driven by the logged-in user's server-returned channels).
- `src/lib/i18n/locales/{vi,en}.ts` → add `nav.chat` ("Trò chuyện" / "Chat") and section keys.
